# gwflow v0.11.0

gwflow v0.11.0 adopts gwf 3.0.0 for managed execution, with native local scheduling, streaming logs, and preserved Task recovery and termination checks.

This corrects the version accidentally published as v0.10.3. The intended release is v0.11.0; the gwf 3 integration and deployment guidance below are retained. The replacement is freshly packaged and qualified under the intended version.

### Highlights

- Managed local execution uses gwf 3 schedulers selected by resolved workflow directory, with independent core and memory budgets.
- `gwflow workers -n 2 --max-memory 4g` budgets two requested cores and 4 GiB of requested memory. A two-core job uses the full core budget. Reservations control scheduling rather than actual process resource use.
- Local jobs write stdout and stderr during execution through native gwf 3 log storage. Log viewing and following retain the selected Submission identity; visibility depends on program and runner flushing.
- Cancellation and timeouts preserve descendant-termination evidence. Resource reservations remain held until termination is established, and unresolved outcomes continue to block unsafe retry or cleanup.
- Native submission recovery preserves the Task lifecycle, including Completion, Reuse, and Repair. The integration also retains controlled Slurm and container execution.

### Compatibility and deployment

This remains a pre-1.0 release. The [compatibility guidance](https://github.com/MOMA-AUH/gwflow/blob/v0.11.0/docs/reference.md#compatibility) continues to apply. Before changing environments, finish or cancel affected jobs and confirm that every computation and lifecycle job and its descendants are inactive. A cancellation request alone does not establish inactivity.

This release requires exactly gwf 3.0.0. The cutover does not migrate earlier workflow state. Keep the earlier environment for inspection or cleanup of earlier runs, and start new gwf 3 runs in separate workflow and storage locations.

Start `gwflow workers` from the same resolved workflow directory as the frontend, using the same global `--file` option when applicable. TCP host and port options are removed; remove retired `backend.local` configuration. Each workflow directory has an independent scheduler, so divide machine capacity across concurrently running workflows. Ordinary `gwf workers` cannot provide gwflow's managed termination guarantees.

Local jobs now default to a one-hour walltime, including preparation and completion jobs. Set explicit limits for long computations, input preparation, and result transfers. Workflow defaults apply to all jobs; Task defaults and target options apply to computation, while `preparation_defaults` and `completion_defaults` govern their respective lifecycle jobs. An effective `walltime=None` uses the one-hour default.

The deployment profile is Linux and Bash with Python 3.12, gwf 3.0.0, and deployment-provided Apptainer 1.5.4 for containers. Automated checks use local workers, real containers, and controlled Slurm commands. Live production-cluster checks are not part of this release validation.

This release uses the qualified native gwf 3 bootstrap for provisional compatibility comparisons. It does not establish compatibility with v0.10.2 workflow state or the future stable compatibility baseline.

### Setup and verification

```sh
conda create -n gwflow-0110 --override-channels -c MOMA-AUH -c gwforg -c conda-forge 'gwflow=0.11.0'
conda activate gwflow-0110
gwf --version
gwflow --version
```
