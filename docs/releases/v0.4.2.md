gwflow v0.4.2 adds registry images to managed Tasks: acquire missing images on the frontend, share the cached SIFs across workflows, and check local and acquired images through the ordinary Input baseline.

### Highlights

- Select anonymously accessible OCI/Docker images with explicit `docker://` references, using tags or pinned digests. Image selection remains per target, so Tasks can combine host commands, local SIFs, and registry images. Workers execute the acquired SIF and never download it.
- Acquire missing image dependencies during `gwf run`, `gwf status`, `gwf explain`, and `gwf run --dry-run`, including images belonging to otherwise reusable Tasks. Pulls report their start and completion or failure on stderr; warm-cache reuse is silent. An acquisition failure preserves Task evidence and retained results and prevents all workflow submissions, while inspection can still report other Tasks.
- Share one image cache across a user's workflows, defaulting to `~/.cache/gwflow/images` with `GWFLOW_IMAGE_CACHE` as the location override. Concurrent frontends coordinate each reference, publish only complete images, and recover from failed or interrupted acquisition without manual lock repair. Usable cached images need no registry access for planning; tags are not polled, and only missing entries are pulled.
- Treat local and acquired images as implicit External inputs, using the same immutable Input baseline as data inputs during preparation, execution, finishing, transfer continuation, repair, and Reuse. Image dependencies are not staged as data unless explicitly declared as such. Changes to image bindings, resolved paths, size, or modification time require fresh computation under the existing activity and ownership guards.
- Preserve cleaned-work Reuse, successful-branch retry, and result repair when a restored image matches the accepted baseline. Reacquiring even the same digest can change local SIF metadata and require a fresh Task attempt. Producer changes propagate to consumers while independent Tasks remain reusable, and work cleanup never removes cached images.

Deployments provide Apptainer and a cache outside managed work, results, and bookkeeping, visible at the same shared path on frontend and compute nodes with matching CPU architectures. The cache must support atomic publication and advisory locks between its frontends. Keep images stable while jobs use them; user removal is not coordinated with workflows, and metadata observations are not content hashes or snapshots. Private-registry authentication, other transports, worker downloads, architecture overrides, refresh, and eviction are outside this release's scope. The pre-1.0 compatibility and transition guidance continues to apply: unsupported factories and records have no automatic conversion, migration, or adoption path, and initialized storage cannot be relocated.

The verified setup is Python 3.12, gwf 2.1.1, and Apptainer 1.5.4. Release preparation CI passed the installed-package and Conda test suites, real Apptainer execution, and local container acceptance checks. The [registry acceptance record](https://github.com/MOMA-AUH/gwflow/blob/v0.4.2/docs/validation-registry.md) documents real frontend acquisition, warm-cache execution, worker baseline enforcement, and fresh recovery on local workers and Slurm, including shared-image observations across BeeGFS clients. Those Slurm checks were recorded during feature acceptance and were not rerun for the version bump. The release workflow built and tested the Conda artifact, published it to the [MOMA-AUH channel](https://anaconda.org/MOMA-AUH/gwflow), then installed the published package and passed the cleanup and Reuse check. See the [README](https://github.com/MOMA-AUH/gwflow/blob/v0.4.2/README.md) and [registry example](https://github.com/MOMA-AUH/gwflow/blob/v0.4.2/examples/registry/workflow.py) for setup and usage.
