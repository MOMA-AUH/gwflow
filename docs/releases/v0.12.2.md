# gwflow v0.12.2

gwflow v0.12.2 protects managed submissions from using a different scheduler directory and keeps the installed JSON status output parseable.

### Highlights

- The first submission records the scheduler directory for a managed run. Subsequent submissions and `gwflow run --dry-run` reject a different workflow directory before changing a Task or submitting a job. Before the first submission, previews leave the directory choice open. Recovery can still use the original Submission’s recorded scheduler evidence. [#455](https://github.com/MOMA-AUH/gwflow/pull/455)
- The installed `gwflow status --json` command sends workflow and plugin shutdown diagnostics to stderr, so stdout contains a single JSON report. [#456](https://github.com/MOMA-AUH/gwflow/pull/456)
- The container reference clarifies which changes to image selection and staged input paths are tracked as Task structure and how a fresh producer attempt affects consumers of its retained outputs. [#457](https://github.com/MOMA-AUH/gwflow/pull/457)

### Compatibility and deployment

Before upgrading, confirm that all affected jobs and descendants are inactive, and keep workflow and storage paths unchanged. For an existing managed run without a recorded scheduler directory, use its original workflow directory for the first submission after upgrading. This is a pre-1.0 release. The supported profile uses Linux and Bash, Python 3.12, exactly gwf 3.0.0, and deployment-provided Apptainer 1.5.4 for container Tasks. [Operating guide](https://github.com/MOMA-AUH/gwflow/blob/v0.12.2/docs/operating.md)
