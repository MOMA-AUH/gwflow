gwflow v0.3.0 adds a managed Task lifecycle: computation runs in disposable work storage, while named retained files are copied into stable results storage. Checked Completion lets finished Tasks remain reusable after their work is removed.

### Highlights

- Define multi-target Tasks and connect them through named retained outputs. Keep Task factories independent of pipeline-selected work and results locations, including separate filesystems.
- Require successful commands, complete declared output sets, and checked retained-result installation before Reuse. Consumers wait for checked Completion of their exact producer attempts.
- Retry failed targets while preserving valid successful work, recover interrupted submissions and result transfers, and repair missing or changed results from verified work. Unresolved submissions block conflicting changes.
- Start fresh attempts when tracked inputs or definitions change, or explicitly refresh selected Tasks with `gwf run --force-task NAME`. Refreshing a producer also refreshes its consumers.
- Preview disposable-work cleanup with `gwf clean-work`, then add `--delete` to remove eligible work while keeping retained results, logs, and Reuse evidence. Select exact inactive attempts with `--attempt` when discarding failed or older work.
- Inspect lifecycle decisions with `gwf status`, `gwf explain`, and `gwf run --dry-run`. The packaged A/B/C example demonstrates cleaning completed producers' work, then adding a consumer that uses only their retained results.

This release changes the Task authoring API. Existing v0.2 factories and records have no automatic conversion, migration, or adoption path; initialized storage cannot be relocated. Managed Workflows do not support ordinary authored top-level targets. Command tracking remains opt-in; package, tool, or environment changes without a tracked effect require explicit force.

The verified setup is Python 3.12 and gwf 2.1.1. Validation covers the local backend, a real Slurm smoke, and separate work/results filesystems; see the [validation record](https://github.com/MOMA-AUH/gwflow/blob/v0.3.0/docs/validation-v0.3.0.md) for evidence and limits. The release workflow built and tested the Conda artifact, published it to the [MOMA-AUH channel](https://anaconda.org/MOMA-AUH/gwflow), then installed the published package and passed the cleanup and Reuse check. See the [README](https://github.com/MOMA-AUH/gwflow/blob/v0.3.0/README.md) for setup and examples.
