gwflow v0.5.1 reduces repeated filesystem work during workflow planning, with shared observations and bounded directory access across status, explain, dry-run, and run.

### Highlights

- Reuse Task job observations and validated producer completion evidence within each planning pass. Shared producers are checked once for matching evidence, reducing repeated reads as more Tasks depend on them.
- Share input and container-image observations across Tasks and targets. Missing files and newly acquired images can still be observed when they become available; observations expire at the end of planning, and submission, recovery, and workers perform fresh checks.
- Reduce repeated directory opens through a bounded set of validated read handles. Pathname, ownership, and replacement checks remain in place, and handles are closed after successful, failed, or interrupted planning.
- Add representative workload and regression tests covering 418 jobs, shared images, command consistency, Task lifecycle behavior, and resource cleanup. The controlled fixture reduced planning file reads from 7,463 to 2,565 and directory opens from 106,369 to 2,703. Metadata checks increased to preserve pathname validation, and overall command times remained broadly similar; these measurements do not establish a fixed speedup on shared storage.

Python and Conda packages now both require Rich `>=15.0.0,<16`. The managed command interface and execution and recovery semantics remain unchanged. Packaged summary and report examples remain version `0.4.0` and accept gwflow `0.5.x`.

The pre-1.0 compatibility and transition guidance continues to apply: finish or deliberately stop existing jobs before switching versions, use the matching old release for inspection or cleanup of old runs, and use separate workflow and storage locations for incompatible records. There is no automatic conversion, migration, or adoption of unsupported factories or records, and initialized storage cannot be relocated. Container execution requires deployment-provided Apptainer; registry images require a shared cache visible at the same path on frontend and compute nodes with matching CPU architectures.

The verified setup is Python 3.12, gwf 2.1.1, and Apptainer 1.5.4. Release preparation CI passed the installed-package and Conda test suites, real Apptainer execution, and local container acceptance checks. The [release workflow](https://github.com/MOMA-AUH/gwflow/actions/runs/37610166279) built and tested the Conda artifact, published it to the [MOMA-AUH channel](https://anaconda.org/MOMA-AUH/gwflow), then installed the published package and passed the cleanup and Reuse check. The [planning validation record](https://github.com/MOMA-AUH/gwflow/blob/v0.5.1/docs/validation-planning-150.json) documents controlled measurements, regression coverage, and their limits. The [registry acceptance record](https://github.com/MOMA-AUH/gwflow/blob/v0.5.1/docs/validation-registry.md) and [container validation record](https://github.com/MOMA-AUH/gwflow/blob/v0.5.1/docs/validation-v0.4.0.md) preserve prior local, Slurm, and BeeGFS observations; those Slurm checks were not rerun for this release.
