gwflow v0.5.2 makes expanded status easier to scan by nesting targets directly beneath their owning Task, with full diagnostics available through explain.

### Highlights

- Use `gwf status --details` to add a Target column to the Task overview. Each Task keeps its primary state, Jobs completed, and brief aggregate detail; preparation, computation targets, and completion appear as child rows with their individual states.
- Select a Task, public job name, or computation-target group to expand the complete owning Task in the same compact view. Dependency order, primary-state filtering, endpoint selection, and whole-workflow validation remain intact.
- Use `gwf explain --details` for full reasons, attempt IDs, workspace and result paths, backend job information, and log paths. Status help and diagnostic hints point to explain. Detailed run and dry-run reports retain their diagnostics.
- Keep the hierarchy readable across terminal layouts: supported terminals show tree branches and state symbols, plain and redirected output use ASCII branches, and narrow terminals stack names and states beneath their Task. `--no-truncate` preserves long names, and wider terminals retain snapshot progress bars.

This changes the output of managed `status --details` and selected-Task status: they now show nested status rows instead of appended diagnostic sections. Ordinary gwf workflow formats are unchanged. Task state, progress calculations, and execution and recovery semantics are unchanged; progress counts preparation, computation, and completion steps, not time or effort. Python and Conda packages continue to require Rich `>=15.0.0,<16`. Packaged summary and report examples remain version `0.4.0` and accept gwflow `0.5.x`.

The pre-1.0 compatibility and transition guidance continues to apply: finish or deliberately stop existing jobs before switching versions, use the matching old release for inspection or cleanup of old runs, and use separate workflow and storage locations for incompatible records. There is no automatic conversion, migration, or adoption of unsupported factories or records, and initialized storage cannot be relocated. Container execution requires deployment-provided Apptainer; registry images require a shared cache visible at the same path on frontend and compute nodes with matching CPU architectures.

The verified setup is Python 3.12, gwf 2.1.1, and Apptainer 1.5.4.
