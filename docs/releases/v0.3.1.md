gwflow v0.3.1 restores the compact, colored `gwf status` tree for everyday monitoring, with full lifecycle diagnostics available through `--details`.

### Highlights

- Keep reusable and pending Tasks on one line, and automatically expand active or problematic Tasks using local target names. Symbols and labels remain readable without color.
- Expand a selected Task with `gwf status TASK`. Use `gwf status --details` for lifecycle reasons, attempts, paths, producer and consumer information, execution submissions, backend job IDs, and log locations.
- Distinguish submitted from running jobs, and keep failed or canceled work visible when a retry is planned. Preserve clear conditions for cleaned-work Reuse, results transfer, repair, waiting for producers, and blocked submission.
- Honor managed status formats, group patterns, and endpoint selection. Flat, summary, and grouped formats report computation targets; `--endpoints` selects Tasks without declared downstream consumers. Ordinary gwf workflows retain their existing status behavior.
- Update the README and packaged A/B/C example to use ordinary status for monitoring and detailed status for debugging.

This patch preserves the v0.3.0 Task authoring API and stored-state format.

The verified setup is Python 3.12, gwf 2.1.1, and the local backend. The release workflow built and tested the Conda artifact, published it to the [MOMA-AUH channel](https://anaconda.org/MOMA-AUH/gwflow), then installed the published package and passed the cleanup and Reuse check. See the [README](https://github.com/MOMA-AUH/gwflow/blob/v0.3.1/README.md) for setup and examples.
