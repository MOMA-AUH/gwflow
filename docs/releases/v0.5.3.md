gwflow v0.5.3 adds decorated Task factories with stable names and a grouped status overview, making repeated Tasks easier to register, inspect, and troubleshoot.

### Highlights

- Define reusable Task factories with `@task_template` and register them with `workflow.task(...)`. Names come from the factory or an explicit alias, with an optional stable instance key. Registration snapshots each definition and reports conflicting Task and public job names. Factory provenance supports naming and grouping without independently invalidating Reuse when a factory moves between modules.
- Group the default `gwf status` overview by factory implementation and effective name prefix. Each group shows its reusable fraction and other primary-state totals; the header reports selected Tasks against the whole workflow. Use `--instances` for individual Task states and completed-job progress, or `--details` to nest every selected Task's jobs beneath it.
- Select visible group, Task, and public job names, with `task:` and `job:` namespaces for overlaps and case-sensitive globs for broader selections. Exact groups open their Task rows, exact Tasks and public jobs expand the owning Task, and wildcard selections retain the overview. Ambiguous and unknown exact names produce explicit errors.
- Keep required workflow notices visible in every status view, including filtered and empty selections. The overview separately previews up to five blocked, failed, and canceled Tasks per category, with complete Task and observed-job totals, omission counts, and shell-quoted commands to inspect every matching Task.
- Preserve complete identifiers, diagnostics, notices, and inspection commands across compact columns and narrow stacked layouts. Supported terminals add colors and state symbols; `--no-color` retains symbols, while `--plain` and redirected output use undecorated text. Status no longer uses decorative frames or progress bars. Full execution diagnostics remain available through `gwf explain --details`.

This changes the managed authoring and status interfaces. Replace `workflow.task_from_template(name, definition)` with decorated factories registered through `workflow.task(definition, alias=name)`; use `key=` for stable repeated instances. Factory definitions must be decorated even for one-off work. Changing a generated Task name changes its identity and does not adopt the old Task's results. Task lifecycle, progress, execution, and recovery semantics remain unchanged, as does ordinary gwf status. Progress counts preparation, computation, and completion steps, not time or effort. Python and Conda packages continue to require Rich `>=15.0.0,<16`. Packaged summary and report examples remain version `0.4.0` and now require gwflow `>=0.5.3,<0.6` for the new factory API.

The pre-1.0 compatibility and transition guidance continues to apply: finish or deliberately stop existing jobs before switching versions, use the matching old release for inspection or cleanup of old runs, and use separate workflow and storage locations for incompatible records. There is no automatic conversion, migration, or adoption of unsupported factories or records, and initialized storage cannot be relocated. Container execution requires deployment-provided Apptainer; registry images require a shared cache visible at the same path on frontend and compute nodes with matching CPU architectures.

The verified setup is Python 3.12, gwf 2.1.1, and Apptainer 1.5.4. Release preparation [CI](https://github.com/MOMA-AUH/gwflow/actions/runs/37915657126) passed 395 installed-package tests, 14 real Apptainer local acceptance tests, and the Conda package test suite (351 passed, 44 container-dependent skips) and packaged-example smoke test. The [release workflow](https://github.com/MOMA-AUH/gwflow/actions/runs/37917935318) built and tested the tagged Conda artifact, published it to the [MOMA-AUH channel](https://anaconda.org/MOMA-AUH/gwflow), then installed the published package and passed the cleanup and Reuse check.
