gwflow v0.7.0 adds Task-level log indexes, retry and attempt history, and managed cancellation. Find a failed job's logs from its Task name, preview the planner's next action, and stop admitted work before ordinary retry or recovery.

### Highlights

- Inspect current jobs with `gwflow logs TASK`, select multiple Tasks with exact names and quoted globs, or use bare `gwflow logs` for all declared and recorded Tasks. Indexes show failures first, identify each attempt and submission, list stdout and stderr availability, and provide commands to read individual streams and preview recovery with `gwflow run TASK --dry-run --details`.
- Add `--history` to include earlier retry submissions and previous Task attempts, explicitly marked as historical. Retries can preserve an attempt while creating new submissions; exact submission names keep earlier logs accessible after retries, fresh attempts, and managed work cleanup. Tasks removed from the workflow remain discoverable as "no longer declared".
- Read recorded logs even when scheduler observations are unavailable. Indexes mark unavailable live state explicitly and do not acquire images or invoke execution planning. One exact public job or submission name still reads its log contents; use `--stderr` for an individual error stream. Task indexes always show both streams, and reject `--stderr`; `--history` applies only to Task indexes.
- Preview cancellation with `gwflow cancel TASK --dry-run`, then request it with `gwflow cancel TASK`. Explicit Task selectors are required, with `cancel '*'` selecting all Tasks deliberately. Requests cover admitted computation and lifecycle jobs in each selected Task's current attempt, including recorded Tasks whose declarations were removed. Every selector must match before requests begin.
- Preserve completed work, retained outputs, and recovery evidence when cancelling. Reports distinguish accepted requests from confirmed inactivity, continue with identifiable jobs after individual failures, and return an error for partial failures or unresolved identities. Once jobs are inactive, ordinary `gwflow run TASK` can retry or recover eligible work without a pause/resume step.
- The installed-package release smoke now covers the complete log, retry/history, cancellation, and recovery journey alongside packaged-example cleanup and Reuse. The packaged summary and report examples remain version `0.4.0` and now accept gwflow `>=0.5.3,<0.8`.

Task names must now differ from public computation and lifecycle job names. For example, a Task named `sample__copy` conflicts with the `copy` job in Task `sample`; workflow construction reports both declarations regardless of their order. Log selection also rejects ambiguities with retained public job or historical submission names. Adjust the relevant Task alias, instance key, or local target name when upgrading.

Cancellation returns after reporting request outcomes; it does not wait for jobs to stop, select older attempts, or expand to upstream or downstream Tasks. Dependent-job handling remains the backend's responsibility, so select additional Tasks explicitly when needed. Accepted cancellation requests do not bypass the inactivity checks required for recovery or cleanup. The existing [pre-1.0 compatibility and storage guidance](https://github.com/MOMA-AUH/gwflow/blob/v0.7.0/docs/reference.md#compatibility) continues to apply.

The verified setup is Linux and Bash with Python 3.12, gwf 2.1.1, and deployment-provided Apptainer 1.5.4. Python and Conda packages require Rich `>=15.0.0,<16`. Registry images require a shared cache visible at the same path on frontend and compute nodes with matching CPU architectures.

The [release workflow](https://github.com/MOMA-AUH/gwflow/actions/runs/38512760531) built and tested the tagged Conda artifact, published it to the [MOMA-AUH channel](https://anaconda.org/MOMA-AUH/gwflow), then installed the published package in a fresh environment and passed both the cleanup/Reuse and troubleshooting/cancellation/recovery smoke checks.
